## <a id="sec-12"></a>12 Agentic Coding Systems

<a id="p-12-agentic-coding-systems-1"></a><!-- para:12-agentic-coding-systems-1 --> **Depth tier:** headline

<a id="p-12-agentic-coding-systems-2"></a><!-- para:12-agentic-coding-systems-2 --> Agents are where the field's centre of gravity moved. An agent wraps a code model in a loop: it observes a repository, takes an action (read a file, edit code, run tests, search), reads the result, and iterates until a task is done. The unit of work is no longer "a function from a docstring" but "a task in a real codebase," which is what SWE-bench measures (<!-- secxref:13 -->[§13](evaluation-and-benchmarks.md#sec-13)).

<a id="p-12-agentic-coding-systems-3"></a><!-- para:12-agentic-coding-systems-3 --> This section covers the loop, the protocols that standardize its tool surface, how systems keep a long task inside a finite context window, the systems themselves, and the central methodological question — how much of the measured performance belongs to the model and how much to the scaffolding around it. It closes with the question a practitioner actually cares about, which has a more uncomfortable answer than the benchmark numbers suggest.

<a id="p-12-agentic-coding-systems-4"></a><!-- para:12-agentic-coding-systems-4 --> The organizing observation is that **the scaffolding has been getting thinner, not thicker**, and that this is a predicted consequence of the base models getting better rather than a matter of fashion.

<!-- sec:12.1 -->
### <a id="sec-12.1"></a>12.1 The Agent Loop: ReAct and the Agent-Computer Interface

<a id="p-121-the-agent-loop-react-and-the-agent-computer-interface-1"></a><!-- para:121-the-agent-loop-react-and-the-agent-computer-interface-1 --> The reasoning substrate of most coding agents is ReAct: prompt the model to interleave reasoning traces with task actions, so that thoughts plan and track the work while actions query the environment and gather observations <!-- cite:31 --> [[31]](references.md#ref-31). ReAct's original results — beating imitation and RL baselines by 34% and 10% absolute on the ALFWorld and WebShop decision-making benchmarks with only a couple of in-context examples — established that reasoning plus acting beats either alone <!-- cite:31 --> [[31]](references.md#ref-31).

<a id="p-121-the-agent-loop-react-and-the-agent-computer-interface-2"></a><!-- para:121-the-agent-loop-react-and-the-agent-computer-interface-2 --> SWE-agent made the sharper claim that the *interface* matters as much as the model. Its thesis is that a language-model agent is a new kind of end user, and that a purpose-built **agent-computer interface (ACI)** — the commands the agent can issue and the format of the feedback it receives — substantially outperforms handing the agent a raw shell <!-- cite:32 --> [[32]](references.md#ref-32). Its four design principles: actions should be simple and easy for an agent to understand; actions should be compact and efficient; environment feedback should be informative but concise; and guardrails, such as a syntax linter wired into the edit command, mitigate error propagation and hasten recovery <!-- cite:32 --> [[32]](references.md#ref-32).

<a id="p-121-the-agent-loop-react-and-the-agent-computer-interface-3"></a><!-- para:121-the-agent-loop-react-and-the-agent-computer-interface-3 --> The payoff was measured directly. With GPT-4 Turbo, SWE-agent resolved 12.47% (286 of 2,294) of the full SWE-bench test set and 18.00% (54 of 300) of SWE-bench Lite, against 3.8% for the prior non-interactive retrieval system, and it ported across models (10.46% full, 13.00% Lite with Claude 3 Opus) <!-- cite:32 --> [[32]](references.md#ref-32). The ablations isolate the interface rather than the model: replacing the custom editor with the raw shell drops Lite from 18.0% to 10.3%, and the edit command's linting guardrail alone accounts for the gap between 15.0% and 18.0% <!-- cite:32 --> [[32]](references.md#ref-32).

<a id="p-121-the-agent-loop-react-and-the-agent-computer-interface-4"></a><!-- para:121-the-agent-loop-react-and-the-agent-computer-interface-4 --> That result was correct, influential, and — within about a year — reversed.

<!-- sec:12.2 -->
### <a id="sec-12.2"></a>12.2 The Interface Thesis and Its Reversal

<a id="p-122-the-interface-thesis-and-its-reversal-1"></a><!-- para:122-the-interface-thesis-and-its-reversal-1 --> **Anthropic's scaffold narrows the action space.** Building an agent for SWE-bench Verified around Claude 3.5 Sonnet, Anthropic reduced the tool surface to two: a persistent Bash tool and a string-replacement editor in which the model specifies `old_str` and `new_str` <!-- cite:98 --> [[98]](references.md#ref-98). The stated design philosophy is the opposite of an elaborate ACI — to give as much control as possible to the language model itself and keep the scaffolding minimal — and the edit format was chosen because string replacement gave the highest reliability among the strategies tried <!-- cite:98 --> [[98]](references.md#ref-98). Gone are SWE-agent's dedicated file-search, directory-search, scroll and goto commands; the model is expected to reach for the shell's own tools itself.

<a id="p-122-the-interface-thesis-and-its-reversal-2"></a><!-- para:122-the-interface-thesis-and-its-reversal-2 --> **Then the action space collapses entirely.** The same group behind SWE-agent subsequently released mini-SWE-agent, roughly a hundred lines, whose action space is *bash and nothing else* — no dedicated edit, search or view command at all. Its own headline claim is that this radically simpler agent still scores above 74% on SWE-bench Verified. That figure is a project self-report rather than a peer-reviewed result and is treated here as such.

<a id="p-122-the-interface-thesis-and-its-reversal-3"></a><!-- para:122-the-interface-thesis-and-its-reversal-3 --> Read against 2024, this is a direct reversal of the ACI thesis by the people who proposed it. SWE-agent's ablation showed that removing the custom editor cost 7.7 points; two years later, removing *everything* cost little enough to ship. Two readings are available and they are not exclusive: the models learned to use a shell competently, and the ACI was always partly compensating for a weakness that has since been trained away.

<a id="p-122-the-interface-thesis-and-its-reversal-4"></a><!-- para:122-the-interface-thesis-and-its-reversal-4 --> The honest caveat is that these are not a controlled comparison. The 18.0% and the 74% were measured on different benchmark variants, with different base models, two years apart. What can be said without a controlled experiment is narrower and still substantial: **the marginal value of a custom interface, holding the task fixed, has fallen far enough that a bash-only agent is now competitive**, which was not true in 2024. <!-- secref:12.6 -->[§12.6](#sec-12.6) treats the attribution problem this creates.

<a id="p-122-the-interface-thesis-and-its-reversal-5"></a><!-- para:122-the-interface-thesis-and-its-reversal-5 --> **The counter-current.** The action space has not simply shrunk in every direction. A parallel line adds *structured code intelligence* — language-server-backed symbol and reference lookup, giving the agent compiler-grade knowledge of definitions and types, and syntax-tree-based semantic retrieval for the conceptual queries a symbol table cannot answer. The tension is real and unresolved: minimal scaffolds bet on the model, structured scaffolds bet on giving it better instruments. As of this writing the evidence for the structured branch is largely vendor and blog material rather than controlled ablation, and this survey marks it as a lead rather than an established result.

<!-- sec:12.3 -->
### <a id="sec-12.3"></a>12.3 Tool Protocols: the Model Context Protocol

<a id="p-123-tool-protocols-the-model-context-protocol-1"></a><!-- para:123-tool-protocols-the-model-context-protocol-1 --> An agent's tools were, until recently, bespoke to each product. The Model Context Protocol is the attempt to standardize that surface, released by Anthropic on 25 November 2024 as an open protocol carrying JSON-RPC 2.0 messages, and explicitly modelled on the Language Server Protocol — which solved the structurally identical problem of every editor needing a custom integration with every language <!-- cite:99 --> [[99]](references.md#ref-99).

<a id="p-123-tool-protocols-the-model-context-protocol-2"></a><!-- para:123-tool-protocols-the-model-context-protocol-2 --> Its architecture names three roles: **hosts** (the application containing the model), **clients** (connectors inside the host, one per server), and **servers** (the services providing capability). What is easy to miss is that the protocol is **bidirectional**. Servers expose three primitives to clients — **Resources** (context and data), **Prompts** (templated messages and workflows), and **Tools** (functions the model can execute). Clients expose three back to servers — **Sampling** (a server may ask the host to run a model call, enabling recursive agentic behaviour), **Roots** (a server may ask about filesystem or URI boundaries), and **Elicitation** (a server may ask the user for more information) <!-- cite:99 --> [[99]](references.md#ref-99).

<a id="p-123-tool-protocols-the-model-context-protocol-3"></a><!-- para:123-tool-protocols-the-model-context-protocol-3 --> For this survey the load-bearing point is architectural, not commercial. A standard tool interface decouples the agent loop from the tool inventory: the same agent gains a capability by connecting a server rather than by shipping new scaffold code. That is what makes the thin-scaffold direction of <!-- secref:12.2 -->[§12.2](#sec-12.2) viable at all — the scaffolding can shrink precisely because the capability surface moved into a protocol.

<a id="p-123-tool-protocols-the-model-context-protocol-4"></a><!-- para:123-tool-protocols-the-model-context-protocol-4 --> Ecosystem claims about the protocol — server counts, adoption breadth, the reported December 2025 transfer of governance to a Linux Foundation body — circulate widely but rest on vendor announcements and third-party analytics rather than on measurement, and are recorded here as reported rather than verified.

### <a id="sec-12.4"></a>12.4 Context Management for Long-Horizon Work

<a id="p-124-context-management-for-long-horizon-work-1"></a><!-- para:124-context-management-for-long-horizon-work-1 --> A repository task can exceed any context window. The mechanisms current systems use to survive that are documented mostly as engineering practice rather than published method; the clearest first-party statement organizes them as *context engineering* — curating the token set across the agent's whole working state rather than writing a better prompt — and names four <!-- cite:100 --> [[100]](references.md#ref-100).

- <a id="p-124-context-management-for-long-horizon-work-2"></a><!-- para:124-context-management-for-long-horizon-work-2 --> **Compaction.** When the window approaches its limit, summarize the trajectory so far and continue from the summary.
- **Structured memory.** Persist state to files outside the context window, which the agent creates, reads, updates and deletes, so information survives compaction <!-- cite:100 --> [[100]](references.md#ref-100).
- **Sub-agent delegation.** Hand a bounded subtask to a fresh agent that returns only a compact summary. The mechanism is context *isolation* as much as division of labour: the sub-agent starts with no knowledge of the parent's history, receiving only an explicit goal payload.
- **Context awareness.** Give the model feedback on its remaining capacity after each tool call, so that it can budget <!-- cite:100 --> [[100]](references.md#ref-100).

<a id="p-124-context-management-for-long-horizon-work-3"></a><!-- para:124-context-management-for-long-horizon-work-3 --> A fifth mechanism is the persistent instruction file — a markdown file at the repository root carrying project-level standing instructions, distinct from per-turn context — which the major agent products converged on during 2025.

<a id="p-124-context-management-for-long-horizon-work-4"></a><!-- para:124-context-management-for-long-horizon-work-4 --> Two cautions. First, almost none of this is evaluated in the literature: these are design patterns with vendor documentation, not methods with ablations, and a survey should not present them as though their benefit had been measured. Second, there is at least one controlled result pointing the *other* way — a 2026 study finds that repository instruction files can reduce task success while increasing cost, the opposite of the intended effect (<!-- secxref:11 -->[§11](retrieval-and-repository-context.md#sec-11)). More context is not monotonically better, and "add an instructions file" is not yet an evidence-backed recommendation.

### <a id="sec-12.5"></a>12.5 A Spectrum of Systems

<a id="p-125-a-spectrum-of-systems-1"></a><!-- para:125-a-spectrum-of-systems-1 --> Coding agents span a design spectrum from structure-aware to generalist to human-in-the-loop.

<a id="p-125-a-spectrum-of-systems-2"></a><!-- para:125-a-spectrum-of-systems-2 --> **Research lineage.** **AutoCodeRover** operates on a program's abstract syntax tree rather than treating it as a bag of files, using syntax-aware code-search APIs and, when a test suite exists, spectrum-based fault localization to focus context; on SWE-bench Lite it resolves 19% (57 issues) at roughly four minutes per issue using GPT-4, at lower cost than a generic shell agent <!-- cite:33 --> [[33]](references.md#ref-33). **OpenHands** (formerly OpenDevin) is an open *platform* rather than a single agent: an event-stream architecture connecting agents, interfaces, and a Docker-sandboxed runtime with a shell, browser, and Python server, plus a built-in evaluation harness; its generalist CodeActAgent reports a 26% SWE-bench Lite resolve rate with Claude 3.5 Sonnet <!-- cite:34 --> [[34]](references.md#ref-34). **Aider** is a terminal pair-programming tool emphasizing reliable diff-style edit formats and a static repository map, reporting 26.3% on SWE-bench Lite as self-reported results on a self-run harness rather than peer-reviewed numbers <!-- cite:48 --> [[48]](references.md#ref-48).

<a id="p-125-a-spectrum-of-systems-3"></a><!-- para:125-a-spectrum-of-systems-3 --> **Deployed products.** By 2026 the deployed systems are the ones most users encounter, and their documentation quality varies enough that the difference is itself a finding. Anthropic's Claude Code, OpenAI's Codex CLI, GitHub Copilot's agent mode, and Google's Jules all have identifiable first-party technical documentation of their loop and tool surface. Codex CLI is a useful contrast with the minimal-scaffold direction: it pairs a general shell tool for reading, searching and running tests with a *separate strict patch envelope* reserved for mutation, deliberately steering the model toward surgical diffs rather than whole-file rewrites.

<a id="p-125-a-spectrum-of-systems-4"></a><!-- para:125-a-spectrum-of-systems-4 --> Two gaps are worth stating plainly rather than papering over. **Cursor** has no first-party architecture documentation that this survey could locate — every available description is third-party. **Devin** has no published technical report; its 2024 launch promised one and no evidence was found that it shipped. Neither observation is a judgment of the product, but a survey that cited blog reconstructions of their internals at the same confidence as OpenHands's paper would be misrepresenting its own evidence.

### <a id="sec-12.6"></a>12.6 Scaffolding versus Base Model

<a id="p-126-scaffolding-versus-base-model-1"></a><!-- para:126-scaffolding-versus-base-model-1 --> The central caveat in reading any of these numbers is that resolved-rate comparisons across systems and time *conflate two improvements*: a better scaffold and a better base model.

<a id="p-126-scaffolding-versus-base-model-2"></a><!-- para:126-scaffolding-versus-base-model-2 --> Both directions have been measured, and they disagree about which dominates. Holding the base model fixed, SWE-agent's ablations move the resolved rate by more than ten points on scaffold changes alone <!-- cite:32 --> [[32]](references.md#ref-32), and AutoCodeRover shows a structure-aware scaffold beating a generic one on the same model <!-- cite:33 --> [[33]](references.md#ref-33). Holding the *scaffold* roughly fixed, the base model has moved results by far more than ten points over the same period.

<a id="p-126-scaffolding-versus-base-model-3"></a><!-- para:126-scaffolding-versus-base-model-3 --> The competitive-programming literature supplies the cleanest controlled version of this comparison, because there the submission budget is a hard rule rather than a design choice. Under the 2024 International Olympiad in Informatics rules, a hand-engineered pipeline built on o1 — subtask decomposition, ten thousand samples per subtask, clustering on model-generated tests, a learned reranker — scored 213 points, where random selection under the same 50-submission cap scored 156; the machinery was worth roughly 60 points <!-- cite:26 --> [[26]](references.md#ref-26). A later model, o3, evaluated under the *same* 50-submission limit with only simple top-score selection over 1,024 samples and none of the hand-built pipeline, scored 395.64 — above the gold-medal threshold <!-- cite:26 --> [[26]](references.md#ref-26). The reported explanation is that the strategies the pipeline had to be given, such as writing brute-force implementations to cross-check an optimized one, emerged from end-to-end reinforcement learning instead <!-- cite:26 --> [[26]](references.md#ref-26). The same trajectory appears on repository tasks: on SWE-bench Verified, 33.2% for GPT-4o, 48.9% for o1, and 71.7% for an early o3 checkpoint <!-- cite:26 --> [[26]](references.md#ref-26).

<a id="p-126-scaffolding-versus-base-model-4"></a><!-- para:126-scaffolding-versus-base-model-4 --> This is the same shape as <!-- secref:12.2 -->[§12.2](#sec-12.2)'s interface reversal arriving from a different direction, and the derivation in <!-- secxref:J.4 -->[§J.4](appendix-j-code-derivations.md#sec-J.4) explains the mechanism: scaffolding exists to convert *coverage* into a *submitted answer*, and as models improve they absorb that selection function.

<a id="p-126-scaffolding-versus-base-model-5"></a><!-- para:126-scaffolding-versus-base-model-5 --> **The practical rule this implies.** A headline agentic number should be read as a *(model, scaffold, date)* triple and never as a property of any one of them. This survey states all three wherever it reports such a figure, and where a component is unknown, says so.

### <a id="sec-12.7"></a>12.7 Multi-Agent Architectures: What Is Claimed, and What Survives

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-1"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-1 --> A recurring proposal is to decompose the loop across specialized roles — planner, coder, reviewer, test designer — or to run candidate agents in parallel. Several systems report head-to-head gains over a single-agent baseline with the base model held fixed. This survey read three of them against their own tables, and the result is that **the claimed effects mostly do not survive the sample sizes they were measured on.**

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-2"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-2 --> **None of the three papers reports a confidence interval, a seed, or a repeated run.** The following tests are therefore this survey's own computation, from the papers' published integer counts, by Fisher's exact test with Wilson intervals:

| Comparison | Treatment | Control | Fisher exact | Verdict |
|---|---|---|---|---|
| Role-decomposition ablation (task-graph system) | 11/50 = 22.0% [12.8, 35.2] | 5/50 = 10.0% [4.3, 21.4] | $p = 0.17$ | **not significant** |
| Debate system vs its baseline | 207/500 = 41.4% [37.2, 45.8] | 194/500 = 38.8% [34.6, 43.1] | $p = 0.44$ | **not significant** |
| Role-decomposition vs single agent (HumanEval) | 131/164 = 79.9% [73.1, 85.3] | 117/164 = 71.3% [64.0, 77.7] | $p = 0.094$ | marginal |
| Task-graph system vs a published single-agent system | 85/300 = 28.3% [23.5, 33.7] | 54/300 = 18.0% [14.1, 22.7] | $p = 0.0036$ | significant — but see below |

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-3"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-3 --> Two of the three flagship ablations have confidence intervals that overlap heavily with their own controls. The one comparison that clears significance is the one that is **not** an ablation: it compares against a different published system, and its budget is not equalized.

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-4"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-4 --> **The budget is the confound, and one paper's own table bounds it.** A role-decomposition system reports gains over a single-agent arm — but its own iteration sweep shows the multi-agent pipeline scoring 74.4 at one refinement iteration and 79.9 at five, against a single-agent arm at 71.3. If the single-agent control was run at one pass, as its description implies, then **roughly 60% of the headline gain is refinement-iteration budget rather than agent decomposition**, and the iteration-matched comparison (74.4 against 71.3) is $p = 0.62$. The paper never states how many iterations the control received, so this is a bound, not a measurement — but it is a bound the paper's own data supplies.

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-5"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-5 --> **One control was never configured by the proposing team at all.** In the task-graph system's comparison table, the request-count and token-cost columns are *byte-identical* between each baseline's "reported" and "reproduced" rows. Those costs were inherited from the baselines' own disclosures rather than re-measured. So its "22% more tokens" is its own measured cost against a competitor's self-reported cost — a cross-basis comparison, not a controlled one. The same system also ran only two of its own four configured plans.

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-6"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-6 --> **Two reporting patterns worth naming, because a reader meeting these numbers second-hand will be misled.** One paper's abstract attributes an accuracy figure and a token-overhead figure to a single "state-of-the-art" baseline; its own table shows these belong to *two different systems* — the best accuracy of one paired with the worst token cost of another. Another reports the same result as "6.7% improvement" and as "2.6 percentage points" in different places, and in one paragraph calls a 14.67-point gain "14.67%" alongside a genuinely relative "5.1%". The arithmetic is consistent; the conventions are not.

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-7"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-7 --> **A resolved loose end.** An earlier evidence round flagged one system as reporting two mutually inconsistent resolve rates. It does not: 28.33% (85/300) is its leaderboard submission and 27.33% (82/300) is its re-run inside its own unified harness, and *every* comparator in the same table shows the same direction and magnitude of gap. That is a reported-versus-reproduced difference, which is ordinary and worth knowing about, not an inconsistency. (The paper's prose does say "84 of 300" where its table says 85; 85 is the arithmetically consistent value.)

<a id="p-127-multi-agent-architectures-what-is-claimed-and-what-survives-8"></a><!-- para:127-multi-agent-architectures-what-is-claimed-and-what-survives-8 --> **Verdict.** The survey's position is unchanged — multi-agent decomposition for code is **not established** — but the reason is now sharper than "the ablations are self-reported." It is that when the significance tests the papers omit are computed from their own counts, two of three headline effects vanish, the surviving one is budget-confounded, and at least one control was demonstrably never configured by the team reporting the margin. This is exactly the `[opt:SIM-BASELINE]` failure mode: the treatment arm gets the design effort and the control inherits a default. Settling it needs a third party running both arms on a shared base model at an equalized token budget, with repeats. Carried to <!-- secxref:18 -->[§18](open-problems-and-roadmap.md#sec-18).

### <a id="sec-12.8"></a>12.8 Does Any of This Make Developers Faster?

<a id="p-128-does-any-of-this-make-developers-faster-1"></a><!-- para:128-does-any-of-this-make-developers-faster-1 --> Every number above measures an agent against a benchmark. The question a practitioner is actually asking is whether the tools make a working developer faster, and the best available evidence is a randomized controlled trial rather than a leaderboard — with a result that runs against both intuition and expert forecast.

<a id="p-128-does-any-of-this-make-developers-faster-2"></a><!-- para:128-does-any-of-this-make-developers-faster-2 --> METR randomized 246 tasks across 16 experienced open-source developers working in mature repositories on which they averaged five years of prior experience, allowing or forbidding early-2025 AI tools (primarily Cursor Pro with Claude 3.5 and 3.7 Sonnet) per task <!-- cite:101 --> [[101]](references.md#ref-101). The measured effect:

| Estimate | Direction and size |
|---|---|
| Developers' forecast, before the study | 24% faster |
| Economics experts' forecast | 39% faster |
| Machine-learning experts' forecast | 38% faster |
| Developers' own estimate, after participating | 20% faster |
| **Measured outcome** | **19% slower** |

<a id="p-128-does-any-of-this-make-developers-faster-3"></a><!-- para:128-does-any-of-this-make-developers-faster-3 --> Every forecast was wrong, in the same direction, including the developers' own retrospective estimate made *after* they had experienced the slowdown <!-- cite:101 --> [[101]](references.md#ref-101). The authors evaluate 21 candidate explanatory properties of their setting, find evidence for some, mixed or no evidence for ten, and evidence against six, concluding that while experimental artefacts cannot be entirely ruled out, the effect is broadly robust across their analyses <!-- cite:101 --> [[101]](references.md#ref-101).

<a id="p-128-does-any-of-this-make-developers-faster-4"></a><!-- para:128-does-any-of-this-make-developers-faster-4 --> **How much this result licenses, and how much it does not.** The population is narrow and deliberately hard: 16 developers, high familiarity with large mature codebases, high quality standards, early-2025 tooling. It is not evidence that AI tools slow developers down in general, and it predates the agentic systems of <!-- secref:12.5 -->[§12.5](#sec-12.5). What it does establish is sharper and harder to dismiss: **in the one setting where the question has been asked with randomization, self-reported speedup and measured speedup had opposite signs.** Any productivity claim resting on practitioner surveys or acceptance rates — which is nearly all of them — inherits that gap and must be discounted accordingly.

<a id="p-128-does-any-of-this-make-developers-faster-5"></a><!-- para:128-does-any-of-this-make-developers-faster-5 --> The wider methodological point is that benchmark resolve rates and developer productivity are different quantities, and the field measures the first far more than the second. A related strand attempts to bridge them by measuring the *length* of task an agent can complete rather than a pass rate <!-- cite:103 --> [[103]](references.md#ref-103), and the evaluation infrastructure needed to compare agents on cost as well as accuracy is itself a recent and explicitly-identified gap <!-- cite:102 --> [[102]](references.md#ref-102) — treated in <!-- secxref:14 -->[§14](compute-cost-and-latency-tradeoffs.md#sec-14). A recent survey of the agentic-programming field organizes the same territory as a taxonomy of behaviours and architectures <!-- cite:104 --> [[104]](references.md#ref-104).
