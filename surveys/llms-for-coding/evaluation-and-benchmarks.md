## <a id="sec-13"></a>13 Evaluation and Benchmarks

<a id="p-13-evaluation-and-benchmarks-1"></a><!-- para:13-evaluation-and-benchmarks-1 --> **Depth tier:** headline

<a id="p-13-evaluation-and-benchmarks-2"></a><!-- para:13-evaluation-and-benchmarks-2 --> How we measure code ability has shaped what the field optimizes, and the benchmark lineage is a story of each generation patching the previous one's blind spot. This section traces that lineage — from function-level pass@k to repository-scale issue resolution — then turns to what the audits of those benchmarks found, and closes with the question of whether the field reports its numbers honestly enough to support the comparisons it makes.

<a id="p-13-evaluation-and-benchmarks-3"></a><!-- para:13-evaluation-and-benchmarks-3 --> The governing principle, stated once: **a leaderboard number is not a capability claim.** The rest of this section is the evidence for how far that principle has to be pushed.

<a id="p-13-evaluation-and-benchmarks-4"></a><!-- para:13-evaluation-and-benchmarks-4 --> The metric itself is derived from first principles in <!-- secxref:J.1 -->[§J.1](appendix-j-code-derivations.md#sec-J.1), including why the intuitive estimator of pass@k is biased and what the measure does and does not capture. The short version needed here: pass@k is a statement about **coverage** — whether the model's output distribution places any mass on a correct program — and it rises with $k$ for reasons that have nothing to do with reliability.

<!-- sec:13.1 -->
### <a id="sec-13.1"></a>13.1 The Foundational Function-Level Benchmarks

<a id="p-131-the-foundational-function-level-benchmarks-1"></a><!-- para:131-the-foundational-function-level-benchmarks-1 --> HumanEval is the origin point: 164 hand-written problems, each a function signature, docstring, body, and an average of 7.7 unit tests, written by hand specifically so functional correctness could be measured rather than text overlap <!-- cite:1 --> [[1]](references.md#ref-1). MBPP complements it with 974 crowd-sourced "mostly basic" Python problems, each with three test cases, plus a 426-problem hand-verified subset; its authors found few-shot performance on the cleaned subset rises noticeably, evidence that crowd-sourced specifications are themselves noisy <!-- cite:35 --> [[35]](references.md#ref-35). Both are scored by pass@k. Their virtue is simplicity and reproducibility; their vice is that they are short, self-contained, now largely saturated, and — as the next subsection shows — under-tested.

<!-- sec:13.2 -->
### <a id="sec-13.2"></a>13.2 The Test-Adequacy Critique

<a id="p-132-the-test-adequacy-critique-1"></a><!-- para:132-the-test-adequacy-critique-1 --> If a benchmark's tests are weak, wrong code passes and scores inflate. EvalPlus made this quantitative: existing benchmarks average fewer than ten tests per problem, so EvalPlus augments HumanEval's tests roughly 80-fold (via LLM-seeded, type-aware mutation) to build HumanEval+, keeping the same 164 problems but vastly stronger tests <!-- cite:36 --> [[36]](references.md#ref-36). Across 26 models, pass@k drops consistently — by up to 19.3% at pass@1 and up to 28.9% at pass@100 — and, crucially, the leaderboard *reorders*: models that the weak tests ranked below ChatGPT overtake it once the tests are adequate <!-- cite:36 --> [[36]](references.md#ref-36). Reported scores were partly artifacts of test insufficiency, not pure capability.

<a id="p-132-the-test-adequacy-critique-2"></a><!-- para:132-the-test-adequacy-critique-2 --> BigCodeBench raises the bar on realism: 1,140 tasks requiring multiple function calls across 139 libraries in 7 domains, with about 5.6 tests per task at 99% average branch coverage; the best model reaches only about 60% versus 97% human performance, a roughly 37-point gap showing that models which ace toy functions cannot reliably compose real library workflows <!-- cite:37 --> [[37]](references.md#ref-37). ClassEval extends the difficulty axis to class-level generation (inter-method dependencies, class structure) and finds all models perform markedly worse than at method level, so method-level ability does not transfer to class-level coding <!-- cite:47 --> [[47]](references.md#ref-47).

<!-- sec:13.3 -->
### <a id="sec-13.3"></a>13.3 Repository-Level and Real-World: SWE-bench

<a id="p-133-repository-level-and-real-world-swe-bench-1"></a><!-- para:133-repository-level-and-real-world-swe-bench-1 --> SWE-bench reframed evaluation entirely: 2,294 task instances built from real GitHub issues and their merged pull requests across 12 popular Python repositories <!-- cite:38 --> [[38]](references.md#ref-38). Given a codebase snapshot and an issue, the model must produce a patch, evaluated by *execution* against the repository's real tests. Its three-stage construction scrapes PRs, keeps those that resolve an issue and contribute tests, and discards any instance lacking a test that flips from fail to pass after the gold patch <!-- cite:38 --> [[38]](references.md#ref-38). "Resolved" means the model's patch makes the fail-to-pass tests pass while not breaking previously passing tests — a behavioral criterion on a large codebase (gold patches average 32.8 edited lines across 1.7 files, against a mean of 3,010 non-test files) <!-- cite:38 --> [[38]](references.md#ref-38). On debut the best model resolved a mere 1.96%, establishing the chasm between saturated function benchmarks and real engineering <!-- cite:38 --> [[38]](references.md#ref-38).

<a id="p-133-repository-level-and-real-world-swe-bench-2"></a><!-- para:133-repository-level-and-real-world-swe-bench-2 --> Two derived sets followed: SWE-bench **Lite** (300 self-contained instances) and SWE-bench **Verified**, a 500-instance subset validated by professional developers after annotation found 38.3% of original instances underspecified and 61.1% with tests that could unfairly fail valid solutions — 68.3% filtered overall, after which scores roughly *doubled*, showing much of the original "difficulty" was benchmark noise <!-- cite:46 --> [[46]](references.md#ref-46).

<!-- sec:13.4 -->
### <a id="sec-13.4"></a>13.4 What SWE-bench Actually Measures: Three Audits

<a id="p-134-what-swe-bench-actually-measures-three-audits-1"></a><!-- para:134-what-swe-bench-actually-measures-three-audits-1 --> Verified fixed the problems its annotators could see. Three subsequent audits found problems they could not, and each one subtracts from what a resolve rate means.

<a id="p-134-what-swe-bench-actually-measures-three-audits-2"></a><!-- para:134-what-swe-bench-actually-measures-three-audits-2 --> **Solution leakage and weak tests.** A systematic audit of successful patches found that 32.67% involved the solution being *directly provided in the issue report or its comments* — the model was reading the answer, not deriving it — and a further 31.08% passed only because the test suite was too weak to distinguish a correct patch from an incorrect or incomplete one <!-- cite:105 --> [[105]](references.md#ref-105). Together those account for 63.75% of the resolved instances examined. Filtering them out moves the measured resolve rate of SWE-agent with GPT-4 from **12.47% to 3.97%** <!-- cite:105 --> [[105]](references.md#ref-105). The same audit notes that over 94% of instances were created before the models' knowledge cutoffs, and when it rebuilds the benchmark from issues created *after* those cutoffs the same system resolves **0.55%** <!-- cite:105 --> [[105]](references.md#ref-105).

<a id="p-134-what-swe-bench-actually-measures-three-audits-3"></a><!-- para:134-what-swe-bench-actually-measures-three-audits-3 --> **Flaky tests.** A repeated-sampling study found that 34 of SWE-bench Lite's 300 problems — 11.3% — have test suites that do not return consistent results when run repeatedly against the *same* candidate patch <!-- cite:107 --> [[107]](references.md#ref-107). The detail that matters most: in 30 of those 34 cases, the flakiness appeared even on the dataset authors' own gold solutions <!-- cite:107 --> [[107]](references.md#ref-107). A benchmark whose ground truth intermittently fails its own tests is measuring the harness as well as the model, and any single-run comparison across systems inherits that noise unquantified.

<a id="p-134-what-swe-bench-actually-measures-three-audits-4"></a><!-- para:134-what-swe-bench-actually-measures-three-audits-4 --> **The denominator is not fixed.** Reported "SWE-bench Verified" percentages are not all computed over the same instance set. At least three denominators circulate — the original 500, and smaller counts used by particular evaluators who exclude instances they judge unusable. This is not necessarily anyone's error; different harnesses may legitimately drop different broken instances. But it means a percentage-point comparison between two vendors' Verified scores is not a comparison of the same quantity unless both denominators are stated, and they usually are not. A survey that ranked systems on such figures would be reporting a metric-basis difference as a capability difference.

<a id="p-134-what-swe-bench-actually-measures-three-audits-5"></a><!-- para:134-what-swe-bench-actually-measures-three-audits-5 --> **What survives.** SWE-bench remains the most important benchmark in this survey, because the *task* it defines — resolve a real issue in a real repository, judged by execution — is the right task. What does not survive is the reading of a resolve rate as a clean capability measurement. The honest form is that a resolve rate is a joint measurement of the model, the scaffold, the harness, the test adequacy of the instances, and the overlap between the instance dates and the training cutoff.

<!-- sec:13.5 -->
### <a id="sec-13.5"></a>13.5 Contamination and Saturation

<a id="p-135-contamination-and-saturation-1"></a><!-- para:135-contamination-and-saturation-1 --> Because benchmarks are public, models may have memorized them, and the question is how much.

<a id="p-135-contamination-and-saturation-2"></a><!-- para:135-contamination-and-saturation-2 --> **Measured directly.** A study combining surface-level matching with abstract-syntax-tree similarity searched the major pretraining corpora for the benchmarks' own gold solutions, and found 12.2% of HumanEval solutions present in The Pile and 18.9% present in The Stack <!-- cite:106 --> [[106]](references.md#ref-106) — the latter despite The Stack having already been through a string-matching decontamination pass for exactly these benchmarks. Surface-level decontamination does not remove semantically equivalent copies.

<a id="p-135-contamination-and-saturation-3"></a><!-- para:135-contamination-and-saturation-3 --> **Designed around.** LiveCodeBench's response is not a better filter but a different construction: continuously collect fresh problems from competitive-programming sites, tag each with its true release date, and evaluate a model only on problems released *after* its training cutoff <!-- cite:39 --> [[39]](references.md#ref-39). Its own diagnostic is the cleanest evidence in this area — two named models "perform considerably worse on problems released since September and November 2023 (their release and cutoff dates respectively)" <!-- cite:39 --> [[39]](references.md#ref-39). The step down at the cutoff date is what contamination looks like when you can see it. The paper is explicit about why it chose construction over filtering: exact and fuzzy matching "can be evaded with simple strategies like rephrasing" <!-- cite:39 --> [[39]](references.md#ref-39).

<a id="p-135-contamination-and-saturation-4"></a><!-- para:135-contamination-and-saturation-4 --> **A second failure mode.** Competitive-programming problems with sparse public tests have false-positive rates of 30–60% — programs that pass the available tests but are wrong — which CodeContests reduces to about 4% by adding mutation-generated tests verified against known-correct solutions <!-- cite:40 --> [[40]](references.md#ref-40).

<a id="p-135-contamination-and-saturation-5"></a><!-- para:135-contamination-and-saturation-5 --> **Saturation.** Benchmarks in this field have a working life measured in months. Aider's original Python-only exercise benchmark was retired for a polyglot successor after reaching the mid-80s. SWE-bench Verified followed: in 2026 OpenAI publicly stopped reporting scores on it, on the grounds that it no longer measures frontier coding capability, citing both saturation and the test-design flaws above. *(That announcement is a vendor blog post that this survey did not acquire, and its specific figures are therefore reported here as claimed rather than verified; the underlying test-quality problems are independently established by the audits in <!-- secref:13.4 -->[§13.4](#sec-13.4).)*

<!-- sec:13.6 -->
### <a id="sec-13.6"></a>13.6 The 2026 Portfolio

<a id="p-136-the-2026-portfolio-1"></a><!-- para:136-the-2026-portfolio-1 --> No single benchmark survives contact with all of the failure modes above, so current practice is a portfolio, each member chosen for the blind spot it covers.

| Benchmark | Task unit | Size | What it adds |
|---|---|---|---|
| HumanEval / MBPP | one function | 164 / 974 | Saturated. Sanity check only. |
| HumanEval+ | one function | 164 | Test adequacy — 80-fold more tests <!-- cite:36 --> [[36]](references.md#ref-36) |
| BigCodeBench | compose library calls | 1,140 | Realism of the call graph <!-- cite:37 --> [[37]](references.md#ref-37) |
| LiveCodeBench | contest problem | 500+, growing | Contamination resistance by construction <!-- cite:39 --> [[39]](references.md#ref-39) |
| SWE-bench Verified | repo issue | 500 | Repository scale, execution-judged <!-- cite:46 --> [[46]](references.md#ref-46) |
| SWE-Bench Pro | long-horizon repo change | 1,865 across 41 repos | Multi-file scale, plus copyleft licensing and held-out splits as a training-inclusion deterrent <!-- cite:108 --> [[108]](references.md#ref-108) |
| SWE-Lancer | paid freelance task | ~1,400 tasks, \$1M in real payouts | Economic value as the unit, including managerial choose-the-proposal tasks <!-- cite:109 --> [[109]](references.md#ref-109) |

<a id="p-136-the-2026-portfolio-2"></a><!-- para:136-the-2026-portfolio-2 --> Two of these deserve comment. **SWE-Bench Pro** attacks contamination with licensing rather than filtering: its public split draws on strong-copyleft repositories, on the theory that a lab is less likely to train on GPL code, and it withholds two further splits entirely <!-- cite:108 --> [[108]](references.md#ref-108). Whether that deterrent holds is an empirical question nobody can answer from outside. **SWE-Lancer** changes the unit of account from "problems solved" to "dollars earned," grading against real freelance tasks and their actual payouts <!-- cite:109 --> [[109]](references.md#ref-109). That reframing is the most direct answer yet to "what is this worth," and it is worth noting that its own paper reports task counts slightly differently in the abstract and the body — a reminder to read the number's definition, not just its magnitude.

<!-- sec:13.7 -->
### <a id="sec-13.7"></a>13.7 Execution, Judges, and the Real-World Gap

<a id="p-137-execution-judges-and-the-real-world-gap-1"></a><!-- para:137-execution-judges-and-the-real-world-gap-1 --> Execution is the spine of all of this. Generated code is untrusted, so it runs in a sandbox — Codex used a gVisor container to prevent host compromise or data exfiltration <!-- cite:1 --> [[1]](references.md#ref-1) — and repository-level harnesses follow an apply-patch, run-tests, log-results procedure with per-instance reproducible environments <!-- cite:38 --> [[38]](references.md#ref-38).

<a id="p-137-execution-judges-and-the-real-world-gap-2"></a><!-- para:137-execution-judges-and-the-real-world-gap-2 --> Using a model as judge is a *complement* to execution for qualities tests miss (readability, style), but the literature is consistent that it is task-dependent and not reliable for *correctness* without execution; surveys treat it as an augmentation, not a replacement <!-- cite:44 --> [[44]](references.md#ref-44). The reliability limit has a mechanism, derived in <!-- secxref:J.4 -->[§J.4](appendix-j-code-derivations.md#sec-J.4): a verifier drawn from the same model as the generator shares its blind spots, and the measured false-endorsement rate varies by an order of magnitude across benchmarks <!-- cite:24 --> [[24]](references.md#ref-24).

<a id="p-137-execution-judges-and-the-real-world-gap-3"></a><!-- para:137-execution-judges-and-the-real-world-gap-3 --> The benchmark-to-reality gap cuts both ways. Benchmarks *overstate* ability through contamination <!-- cite:106 --> [[106]](references.md#ref-106) and weak tests <!-- cite:36 --> [[36]](references.md#ref-36), <!-- cite:105 --> [[105]](references.md#ref-105), and they *understate* it through broken instances — the 68.3% filtering that produced Verified <!-- cite:46 --> [[46]](references.md#ref-46). And a benchmark score is not a productivity measurement at all: the one randomized trial of the question found experienced developers 19% *slower* with AI tooling while believing themselves 20% faster (<!-- secxref:12.8 -->[§12.8](agentic-coding-systems.md#sec-12.8)).

<!-- sec:13.8 -->
### <a id="sec-13.8"></a>13.8 Does the Field Report Its Numbers Honestly?

<a id="p-138-does-the-field-report-its-numbers-honestly-1"></a><!-- para:138-does-the-field-report-its-numbers-honestly-1 --> Everything above assumes the reported numbers can be compared. A pilot audit tested that assumption directly, scoring twelve canonical benchmark papers on five disclosure dimensions — benchmark identity, harness specification, inference settings, cost reporting, and failure breakdown <!-- cite:110 --> [[110]](references.md#ref-110). The result:

| Paper class | Mean disclosure score (of 1.0) |
|---|---|
| Eight agent-benchmark papers | **0.38** |
| Four classical static-benchmark papers | **0.66** |

<a id="p-138-does-the-field-report-its-numbers-honestly-2"></a><!-- para:138-does-the-field-report-its-numbers-honestly-2 --> The largest single gap was cost: **none of the eight** agent-benchmark papers disclosed inference cost in any form <!-- cite:110 --> [[110]](references.md#ref-110). The audit also records that every zero it assigned was an *omission* rather than a misstatement, and argues the fix is to instrument the evaluation harness to emit disclosures automatically rather than to demand stricter reviewing <!-- cite:110 --> [[110]](references.md#ref-110).

<a id="p-138-does-the-field-report-its-numbers-honestly-3"></a><!-- para:138-does-the-field-report-its-numbers-honestly-3 --> Set that against <!-- secref:13.4 -->[§13.4](#sec-13.4). A benchmark with 11.3% flaky instances, evaluated in a single run, with no confidence interval, on an unstated denominator, compared against a rival system running a different scaffold on a different date — that is the modal published comparison in agentic coding, and it does not support the one-or-two-point distinctions routinely drawn from it.

<a id="p-138-does-the-field-report-its-numbers-honestly-4"></a><!-- para:138-does-the-field-report-its-numbers-honestly-4 --> **What this survey does about it.** Every agentic figure quoted here carries its model, scaffold and date. Where a denominator is unstated it is not silently assumed. Where a number could not be traced to a source that was actually read, it is either omitted or marked as reported-not-verified. The practical guidance in <!-- secxref:17 -->[§17](design-guidance.md#sec-17) follows the same rule: prefer execution-based, contamination-resistant, adequately-tested benchmarks; read any single number with its date and test-suite quality in mind; and treat the function-level classics as saturated sanity checks rather than measures of engineering competence.
