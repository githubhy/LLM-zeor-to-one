## <a id="sec-7"></a>7 Pretraining Objectives, Tokenization, and Scaling

<a id="p-7-pretraining-objectives-tokenization-and-scaling-1"></a><!-- para:7-pretraining-objectives-tokenization-and-scaling-1 --> **Depth tier:** headline

<a id="p-7-pretraining-objectives-tokenization-and-scaling-2"></a><!-- para:7-pretraining-objectives-tokenization-and-scaling-2 --> Section 3 introduced the autoregressive objective and the fill-in-the-middle transform in the abstract. This section is the engineering reality: how FIM is actually configured in production code models, how their tokenizers are built, how repositories are packed into training sequences, and what is known — and not known — about scaling code models.

<!-- sec:7.1 -->
### <a id="sec-7.1"></a>7.1 Fill-in-the-Middle in Production

<a id="p-71-fill-in-the-middle-in-production-1"></a><!-- para:71-fill-in-the-middle-in-production-1 --> The canonical FIM study recommends a 50% FIM rate, character-level spans, and joint training on the prefix-suffix-middle (PSM) and suffix-prefix-middle (SPM) orderings <!-- cite:5 --> [[5]](references.md#ref-5). The transformation itself, and the chain-rule argument for why a strictly left-to-right model can nevertheless learn to condition on the suffix, are derived in <!-- secxref:J.2 -->[§J.2](appendix-j-code-derivations.md#sec-J.2); that derivation also explains why the rate can go as high as 90% at no cost to left-to-right quality but degrades at 100%. Production code models adopt these settings with remarkable consistency. StarCoder applies FIM at the character level with a rate of 0.5, mixing PSM and an SPM variant equally <!-- cite:8 --> [[8]](references.md#ref-8). DeepSeek-Coder uses a 0.5 FIM rate in PSM mode applied at the document level before packing, and ablates 0%, 50%, and 100% FIM rates plus a masked-span-prediction alternative, settling on 50% PSM as the best trade between infilling and left-to-right quality <!-- cite:10 --> [[10]](references.md#ref-10). Code Llama applies FIM with probability 0.9, half PSM and half SPM, and notably suppresses the leading space that its SentencePiece tokenizer would otherwise insert, to limit the train/inference distribution shift between ordinary generation and infilling <!-- cite:6 --> [[6]](references.md#ref-6). Qwen2.5-Coder carries FIM into the repository-level stage with dedicated sentinel tokens <!-- cite:11 --> [[11]](references.md#ref-11). The lesson is that FIM is no longer a research option but a default, configured within a narrow band the field has converged on.

<!-- sec:7.2 -->
### <a id="sec-7.2"></a>7.2 Tokenizer Design at Scale

<a id="p-72-tokenizer-design-at-scale-1"></a><!-- para:72-tokenizer-design-at-scale-1 --> Code tokenizers are byte-level BPE with a digit-splitter and GPT-2-style pre-tokenization, sized to the code-plus-text mixture. StarCoder and StarCoder 2 use a 49,152-token vocabulary (including FIM sentinels) and report that raising it to 100k "did not improve performance," so they kept it small <!-- cite:9 --> [[9]](references.md#ref-9). DeepSeek-Coder uses 32,000 tokens <!-- cite:10 --> [[10]](references.md#ref-10); Qwen2.5-Coder inherits Qwen2.5's 151,646-token vocabulary and adds code/FIM special tokens <!-- cite:11 --> [[11]](references.md#ref-11). The recurring code-specific moves — whitespace-run tokens (Section 3), cross-whitespace merges, digit splitting — all target code's redundancy and numeric literals. One caveat for the careful reader: the published reports give vocabulary sizes and pre-tokenization rules but generally not per-language *fertility* tables (tokens per byte), so cross-model tokenizer-efficiency comparisons should be made qualitatively rather than from a precise published number.

<!-- sec:7.3 -->
### <a id="sec-7.3"></a>7.3 Repository-Level Pretraining and Long Context

<a id="p-73-repository-level-pretraining-and-long-context-1"></a><!-- para:73-repository-level-pretraining-and-long-context-1 --> Function-level pretraining teaches local syntax; repository-level pretraining teaches cross-file structure — that a symbol is defined in one file and used in another. The two published strategies differ instructively. DeepSeek-Coder performs dependency-aware ordering: it parses import statements (`import` in Python, `using` in C#, `#include` in C) to build a file dependency graph, runs a topological sort, and concatenates files so that a file appears after its dependencies, prepending each with a path comment <!-- cite:10 --> [[10]](references.md#ref-10). StarCoder 2 instead concatenates each repository's files in *random* order, delimited by a file-separator token, treating cross-file learning as a consequence of co-occurrence rather than explicit ordering <!-- cite:9 --> [[9]](references.md#ref-9). Both pair repository packing with longer contexts: StarCoder uses 8k, StarCoder 2 extends a 4k base to 16k via continued pretraining with a sliding window and increased RoPE base frequency, DeepSeek-Coder trains at 16k, and Qwen2.5-Coder extends to 128k via length extrapolation (YARN) in its repository stage <!-- cite:8 --> [[8]](references.md#ref-8), <!-- cite:9 --> [[9]](references.md#ref-9), <!-- cite:10 --> [[10]](references.md#ref-10), <!-- cite:11 --> [[11]](references.md#ref-11). Long context and retrieval are complementary answers to the same problem (Section 11): how to give the model the parts of a large repository that matter.

<!-- sec:7.4 -->
### <a id="sec-7.4"></a>7.4 Scaling and Data Mixture

<a id="p-74-scaling-and-data-mixture-1"></a><!-- para:74-scaling-and-data-mixture-1 --> Code models complicate the clean compute-optimal scaling story in two ways. First, the **mixture** matters and is counterintuitive. Qwen2.5-Coder ablates code:text:math ratios and finds that 70:20:10 outperforms higher-code mixtures — more code is not strictly better, because math and natural-language data improve code performance <!-- cite:11 --> [[11]](references.md#ref-11). DeepSeek-Coder uses 87% source code, 10% code-related English, and 3% other natural language <!-- cite:10 --> [[10]](references.md#ref-10). Second, deployment economics push models to **over-train** relative to the compute-optimal (Chinchilla) point: StarCoder 2 trains its 3B, 7B, and 15B models on 3.3-to-4.3 trillion tokens — far past the token count a compute-optimal law would prescribe — because the goal is inference efficiency, not training efficiency <!-- cite:9 --> [[9]](references.md#ref-9). Notably, none of these reports fit a code-specific scaling law with explicit exponents; the strongest scaling claim in the corpus is phi-1's qualitative one (Section 6), that data quality changes the shape of the curve rather than just shifting along it <!-- cite:12 --> [[12]](references.md#ref-12). The honest state of the art is that code scaling is governed by data quality and mixture at least as much as by the parameter-token frontier, and the precise functional form remains an open question (Section 18).

<!-- sec:7.5 -->
### <a id="sec-7.5"></a>7.5 Does Code Data Improve General Reasoning?

<a id="p-75-does-code-data-improve-general-reasoning-1"></a><!-- para:75-does-code-data-improve-general-reasoning-1 --> This is the most-repeated claim in the folklore around code models, and it is repeated far more often than it is measured. An earlier evidence round for this survey could not find a source that measures it at all, and recorded it as unverified. That was too pessimistic: the measurements exist. They are also weaker, narrower, and more conditional than the folklore, and this subsection is written as a deflation rather than a confirmation.

<a id="p-75-does-code-data-improve-general-reasoning-2"></a><!-- para:75-does-code-data-improve-general-reasoning-2 --> **There is one controlled experiment, not a literature.** Of the three studies that bear on the question, exactly one runs a controlled code-versus-no-code *pretraining* ablation: Aryabumi et al. <!-- cite:122 --> [[122]](references.md#ref-122). The other two cannot isolate pretraining code — one compares differently-pretrained checkpoints <!-- cite:123 --> [[123]](references.md#ref-123), the other varies only instruction-tuning data on models whose pretraining already contained code <!-- cite:124 --> [[124]](references.md#ref-124). Three papers is not three confirmations.

<a id="p-75-does-code-data-improve-general-reasoning-3"></a><!-- para:75-does-code-data-improve-general-reasoning-3 --> **The headline, with the basis attached.** Against a text-only baseline, the best code-containing recipe gains **+8.2% relative on natural-language reasoning**, +4.2% on world knowledge, and 12 times on code <!-- cite:122 --> [[122]](references.md#ref-122). The reasoning score is an average over eleven zero-shot benchmarks. Two qualifications travel with that number and are usually dropped:

- <a id="p-75-does-code-data-improve-general-reasoning-4"></a><!-- para:75-does-code-data-improve-general-reasoning-4 --> It is measured at **470M parameters only.** The paper's 2.8B ablation compares code-containing variants against *each other*; no text-only 2.8B model exists in it. The paper's statement that its findings hold from 470M to 2.8B refers to the initialization *ordering*, not to the code-versus-no-code effect.
- It is a **pre-cooldown** comparison, and the paper's own Table 2 contains the post-cooldown one.

<a id="p-75-does-code-data-improve-general-reasoning-5"></a><!-- para:75-does-code-data-improve-general-reasoning-5 --> **The post-cooldown comparison is the honest one, and it is much smaller.** Reading Table 2 directly — this is the survey's own computation from the paper's cells, not a claim the authors make — the best code recipe after cooldown scores 54.9 on reasoning against the text-only model's 54.1, a gain of **+0.8 accuracy points (+1.5% relative)**. On world knowledge the **text-only model wins**, 11.1 against 10.9. On code the ratio is 1.3 times, not 12. The mechanism is visible in the same table: every cooldown adds 32B text and **8B code** tokens, so the "text-only" arm is not code-free after cooldown — and roughly 8B late code tokens recover most of what 200B tokens of code-heavy pretraining bought. That single observation does more to explain current practice than the headline does.

<a id="p-75-does-code-data-improve-general-reasoning-6"></a><!-- para:75-does-code-data-improve-general-reasoning-6 --> **The dose-response is the most transferable result.** Sweeping the code fraction, 25% is optimal for the reasoning-plus-knowledge average; 0% code is 3.4% relative *worse* than 25%; reasoning is roughly flat from 0% to 75%; and it collapses only at 100%, by 18.3% relative <!-- cite:122 --> [[122]](references.md#ref-122). World knowledge is penalized monotonically throughout (−3.4% at 25%, −31% at 75%, −86% at 100%). So the defensible form of the claim is not "code improves reasoning" but **"some code is better than none, a quarter is about right, and an all-code diet is destructive"** — which is, in fact, roughly where production mixtures sit.

<a id="p-75-does-code-data-improve-general-reasoning-7"></a><!-- para:75-does-code-data-improve-general-reasoning-7 --> **The two stage studies agree at the sub-task level and should not be read as a conflict.** They share no benchmark, model family, or language. What both find is that *instruction-tuning-stage* code is inconsistent underneath a positive aggregate. Instruction tuning on code raises all six model families tested, by +1.5 to +10.3 points, but the domain where it helps most is a set of four synthetic string-manipulation tasks — the domain nearest to code — while arithmetic word problems are better served by general or half-and-half data <!-- cite:124 --> [[124]](references.md#ref-124). The gradient runs with distance from code, which is more interesting than the aggregate. And one paper's abstract describes its transfer as occurring "almost without negative transfer" while its own tables show natural-language-inference and reading-comprehension scores falling <!-- cite:123 --> [[123]](references.md#ref-123).

> <a id="p-75-does-code-data-improve-general-reasoning-8"></a><!-- para:75-does-code-data-improve-general-reasoning-8 --> **Note — read the small movements with care.** None of the three papers reports a seed, a confidence interval, or an error bar. Every delta quoted above is a single-run point estimate. One of them is worse than that: a headline "logic" improvement from 36.36 to 40.90 is measured on a 22-question subject, where every reported value is an exact multiple of $1/22$ — the improvement is **one question**, with a Wilson interval spanning roughly 21% to 55%. Movements of one to three points in this literature should be treated as unresolved, not as effects.

<a id="p-75-does-code-data-improve-general-reasoning-9"></a><!-- para:75-does-code-data-improve-general-reasoning-9 --> **What the survey therefore asserts.** Code in the pretraining mixture is worth including, at a minority share, and the evidence for that is real. The strong form of the folklore — that code data is a general reasoning catalyst, at scale, robustly — rests on one 470M-parameter ablation whose advantage largely disappears once both arms are cooled down on data that includes code. Anyone repeating the claim should say which version they mean.
