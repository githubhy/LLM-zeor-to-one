## <a id="sec-11"></a>11 Retrieval and Repository Context

<a id="p-11-retrieval-and-repository-context-1"></a><!-- para:11-retrieval-and-repository-context-1 --> **Depth tier:** load-bearing

<a id="p-11-retrieval-and-repository-context-2"></a><!-- para:11-retrieval-and-repository-context-2 --> A code model's context window is small next to a repository. Everything in this section is a strategy for choosing what goes in it. The field has two families — retrieve chunks by similarity, or let an agent *search* the way a developer does — and a live dispute about which wins. This section reports what has actually been measured, which is less than the dispute assumes.

<!-- sec:11.1 -->
### <a id="sec-11.1"></a>11.1 Repository-Level Completion by Retrieval

<a id="p-111-repository-level-completion-by-retrieval-1"></a><!-- para:111-repository-level-completion-by-retrieval-1 --> RepoCoder frames the problem as iterative: retrieve candidate context, generate, then use the generation itself as a better retrieval query on the next round, because the code you are about to write is a better description of what you need than the code you have already written <!-- cite:30 --> [[30]](references.md#ref-30). That loop is the ancestor of the agentic approach in <!-- secref:11.3 -->[§11.3](#sec-11.3): both replace a single similarity lookup with a feedback cycle.

<a id="p-111-repository-level-completion-by-retrieval-2"></a><!-- para:111-repository-level-completion-by-retrieval-2 --> The structural alternative gives the model a *map* rather than a bag of chunks. A taxonomy of the field splits it by **primary retrieval substrate**: graph-based, where the core mechanism depends on an explicitly constructed code graph, and non-graph, where retrieval runs over flat text even if lightweight structural signals are injected <!-- cite:115 --> [[115]](references.md#ref-115). The graph family is well enough developed to have a default shape — a three-tier module/class/function abstraction over containment and invocation edges, out of a vocabulary of six edge types (contain, import, inherit, invoke, data flow, control flow) and five node granularities <!-- cite:115 --> [[115]](references.md#ref-115).

<a id="p-111-repository-level-completion-by-retrieval-3"></a><!-- para:111-repository-level-completion-by-retrieval-3 --> **RepoGraph** is the concrete instance, and its headline needs decomposing. It reports a 32.8% relative improvement on SWE-bench when plugged into existing frameworks <!-- cite:111 --> [[111]](references.md#ref-111). That figure is an *unweighted mean of four relative gains* — 99.63%, 8.56%, 12.26%, 10.91% — and the 99.63% term is one framework moving from 8 to 16 resolved instances out of 300. In absolute terms the four gains are +2.00 to +2.66 percentage points, six to eight net instances out of 300, reported without repeated runs, confidence intervals, or a significance test. The direction is consistent across four frameworks, which is the real evidence; the 32.8% is an artifact of averaging ratios against a near-floor baseline. Note also that RepoGraph's own baseline is BM25 file-level retrieval, and no dense retriever appears in that paper at all.

<!-- sec:11.2 -->
### <a id="sec-11.2"></a>11.2 How Good Is Code Retrieval, in Absolute Terms?

<a id="p-112-how-good-is-code-retrieval-in-absolute-terms-1"></a><!-- para:112-how-good-is-code-retrieval-in-absolute-terms-1 --> Before comparing retrieval against agents it is worth knowing how well retrieval works at all. On CoIR, a ten-dataset code-retrieval benchmark, the best model averages **56.26 NDCG@10**, BM25 averages 29.79, and the hardest subset tops out at 26.52 <!-- cite:114 --> [[114]](references.md#ref-114). That is the backdrop for everything below: code retrieval is not a solved component that agents are unnecessarily replacing. It is a weak one.

<!-- sec:11.3 -->
### <a id="sec-11.3"></a>11.3 Agentic Search versus Embedding Retrieval

<a id="p-113-agentic-search-versus-embedding-retrieval-1"></a><!-- para:113-agentic-search-versus-embedding-retrieval-1 --> An earlier draft of this survey stated that no head-to-head comparison of agentic search against embedding retrieval could be found. **That is superseded — but narrowly, and the qualifications matter more than the result.**

<a id="p-113-agentic-search-versus-embedding-retrieval-2"></a><!-- para:113-agentic-search-versus-embedding-retrieval-2 --> LocAgent evaluates one sparse and four embedding retrievers against five agent and procedural frameworks on a single code-localization task with a single metric family, over 274 instances filtered from SWE-bench Lite <!-- cite:112 --> [[112]](references.md#ref-112). It is one comparison, published by the authors of the winning method, with the control at an off-the-shelf default. Read as such, it shows three things.

<a id="p-113-agentic-search-versus-embedding-retrieval-3"></a><!-- para:113-agentic-search-versus-embedding-retrieval-3 --> **The gap is granularity-dependent.** At file level, the best embedder reaches 84.67 Acc@5 against LocAgent's 94.16 — but that same embedder also *beats* three of the agent configurations: a procedural framework at 79.56, and two agent frameworks at 68.98 and 73.72. At function level the gap widens sharply, 58.76 against 77.37, some 18.6 points or roughly 51 of 274 instances — large enough to survive any plausible single-run noise. The defensible statement is that structure-aware agentic localization helps most where *granularity is finest*, and that at file level a good embedder is competitive with several published agents.

<a id="p-113-agentic-search-versus-embedding-retrieval-4"></a><!-- para:113-agentic-search-versus-embedding-retrieval-4 --> **The backbone is confounded with the mechanism.** Every agent configuration that loses to the best embedder runs a weaker backbone model or is procedure-based; every configuration that wins runs the stronger one. No arm holds the language model constant. Following the triage discipline of `calibration-residuals`, the margin is jointly attributable to `{graph-structured search, backbone model quality, baseline indexing handicap}` and this experiment does not separate them.

<a id="p-113-agentic-search-versus-embedding-retrieval-5"></a><!-- para:113-agentic-search-versus-embedding-retrieval-5 --> **The control is disclosed as handicapped.** The paper's own appendix concedes that the retrieval baselines were run with flat rather than hierarchical indexing. A comparative margin published without that disclosure would not be citable; with it, the honest reading is that the embedding arm was not run at its best operating point.

<a id="p-113-agentic-search-versus-embedding-retrieval-6"></a><!-- para:113-agentic-search-versus-embedding-retrieval-6 --> **And the comparison prices only one side.** The agent configurations run five to fifteen model rounds at roughly \$0.46 to \$0.83 per instance; the retrievers are a single forward pass and are never costed <!-- cite:112 --> [[112]](references.md#ref-112). An accuracy-only comparison between a method that makes one call and a method that makes fifteen is not a comparison of methods, it is a comparison of budgets (<!-- secxref:14 -->[§14](compute-cost-and-latency-tradeoffs.md#sec-14)).

<a id="p-113-agentic-search-versus-embedding-retrieval-7"></a><!-- para:113-agentic-search-versus-embedding-retrieval-7 --> **Localization accuracy is a weak predictor of the thing you care about.** The same paper reports that +14.97 points of file-level localization accuracy converts to **+1.61 points** of end-to-end resolution, 26.31% to 27.92% <!-- cite:112 --> [[112]](references.md#ref-112). Finding the right file is necessary and nowhere near sufficient, and a retrieval method should be judged on the downstream number rather than the intermediate one.

<a id="p-113-agentic-search-versus-embedding-retrieval-8"></a><!-- para:113-agentic-search-versus-embedding-retrieval-8 --> **A note on how this dispute is sourced.** The most-cited framing of the agentic-search turn — that replacing static embeddings with live filesystem commands inside a plan-act-observe loop improves precision — appears in a recent survey with no measurement attached on either side, and its adjacent citation resolves to a vendor product page <!-- cite:115 --> [[115]](references.md#ref-115). The mechanism is plausible and may well be right. It is not, at the time of writing, established.

### <a id="sec-11.4"></a>11.4 Long Context versus Retrieval

<a id="p-114-long-context-versus-retrieval-1"></a><!-- para:114-long-context-versus-retrieval-1 --> The obvious question is whether a large enough context window makes all of this unnecessary. The measured answer is that repository context helps, but **not monotonically in repository size**. Sweeping project size on a long-context code-completion benchmark, the benefit of adding repository context runs +5%, +26%, +35%, +17% for small, medium, large and huge projects respectively <!-- cite:113 --> [[113]](references.md#ref-113). The benefit *peaks* at large and *degrades* at huge — precisely where the intuition "just put the repository in the window" would predict it should be greatest.

<a id="p-114-long-context-versus-retrieval-2"></a><!-- para:114-long-context-versus-retrieval-2 --> That shape is the argument for retrieval surviving long context: past some size, the limiting factor stops being what the window can hold and becomes what the model can use. The measurement carries the usual caveats — a single 7B model, a 16K context budget, exact-match scoring, no seeds and no confidence intervals — so treat the peak location as indicative rather than pinned.

<a id="p-114-long-context-versus-retrieval-3"></a><!-- para:114-long-context-versus-retrieval-3 --> A related and more practical finding sits in <!-- secxref:12.4 -->[§12.4](agentic-coding-systems.md#sec-12.4): a controlled 2026 study found that repository instruction files can *reduce* task success while raising cost. More context is not monotonically better at either scale.

### <a id="sec-11.5"></a>11.5 What the Field Publishes, and What It Deploys

<a id="p-115-what-the-field-publishes-and-what-it-deploys-1"></a><!-- para:115-what-the-field-publishes-and-what-it-deploys-1 --> Two composition statistics are worth carrying, both from the same systematic review of 152 papers screened from 853 candidates over 2023 to early 2026 <!-- cite:115 --> [[115]](references.md#ref-115), and both to be read as statements about the *published literature* rather than about deployment.

- <a id="p-115-what-the-field-publishes-and-what-it-deploys-2"></a><!-- para:115-what-the-field-publishes-and-what-it-deploys-2 --> **Autonomy.** 71.1% of the surveyed systems are non-agentic, 7.9% use explicit iterative feedback without autonomous planning, and 21.1% are autonomous planners with tools. The research literature is still mostly retrieval-shaped even as products move agentic.
- **Language.** Python dominates by a factor of more than two over the next language (111 systems against 50 for Java, then single digits for everything else), and the review names the Python-only scope of the dominant benchmark as a compounding bias. The conclusions of this section are, to a first approximation, conclusions about Python.

<a id="p-115-what-the-field-publishes-and-what-it-deploys-3"></a><!-- para:115-what-the-field-publishes-and-what-it-deploys-3 --> The practical synthesis for a builder: retrieval quality in absolute terms is mediocre (<!-- secref:11.2 -->[§11.2](#sec-11.2)), structure beats flat text where it can be extracted (<!-- secref:11.1 -->[§11.1](#sec-11.1)), agentic search is ahead at fine granularity but on evidence that does not separate mechanism from backbone (<!-- secref:11.3 -->[§11.3](#sec-11.3)), and neither approach is obviated by a bigger window (<!-- secref:11.4 -->[§11.4](#sec-11.4)). The honest state of the art is that this is an open engineering question with one published comparison, not a settled one.
