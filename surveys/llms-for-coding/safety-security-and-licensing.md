## <a id="sec-16"></a>16 Safety, Security, Licensing, and Risk

<a id="p-16-safety-security-licensing-and-risk-1"></a><!-- para:16-safety-security-licensing-and-risk-1 --> **Depth tier:** load-bearing

<a id="p-16-safety-security-licensing-and-risk-2"></a><!-- para:16-safety-security-licensing-and-risk-2 --> Code models inherit the general risks of LLMs and add several specific to the modality: they write insecure code that compiles and runs, they expand the attack surface when wired into autonomous agents, they will game a verifier that can be gamed, and they raise unresolved questions about the licensing of the code they were trained on. This section treats each in turn, and is careful about which claims are measured and which are asserted — the gap between the two is unusually wide here.

<!-- sec:16.1 -->
### <a id="sec-16.1"></a>16.1 Insecure Code Generation, and Whether It Improved

<a id="p-161-insecure-code-generation-and-whether-it-improved-1"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-1 --> The foundational result is "Asleep at the Keyboard": across 89 scenarios spanning MITRE's top-25 weakness classes, producing 1,689 programs, approximately **40% were vulnerable** <!-- cite:41 --> [[41]](references.md#ref-41). That headline is an all-axes, all-language figure (three prompt axes, Python, C and Verilog), and it is the number usually quoted.

<a id="p-161-insecure-code-generation-and-whether-it-improved-2"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-2 --> **Has it improved?** A targeted replication re-ran the *same* 29 Python scenarios across the *same* 12 weakness classes with a later Copilot and a later static analyzer <!-- cite:128 --> [[128]](references.md#ref-128). Comparing like with like requires the original's Python subset rather than its all-language headline:

| | Scenarios | Programs | Vulnerable | Rate | Wilson 95% |
|---|---|---|---|---|---|
| Original (Python subset) | 29 | 571 | 219 | **38.35%** | [34.46, 42.41] |
| Replication (2023) | 29 | 411 | 112 | **27.25%** | [23.17, 31.75] |

<a id="p-161-insecure-code-generation-and-whether-it-improved-3"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-3 --> An 11.1-point absolute drop, roughly 29% relative. Three qualifications, in descending order of importance.

- <a id="p-161-insecure-code-generation-and-whether-it-improved-4"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-4 --> **The aggregate hides an inversion.** Hard-coded-credential scenarios went to zero vulnerable across all three of their instances, while deserialization got *worse* — one scenario returning 17 of 22 vulnerable against 5 of 19 originally, and another newly producing a vulnerable top-ranked suggestion. A reader who takes "27%" as uniform improvement will be wrong about the classes that regressed.
- **The denominators are not composed the same way.** The original sampled up to 25 completions per scenario and de-duplicated by token sequence; the replication collected up to 55 and de-duplicated by syntax-tree similarity while discarding non-compiling code. That is a metric-basis difference, and it means the two rates are close-but-not-identical quantities.
- **The intervals above are floors.** Suggestions cluster within 29 scenarios whose individual rates run from 0 of 25 to 19 of 32, so a binomial interval understates the true uncertainty; neither paper reports a clustered one.

<a id="p-161-insecure-code-generation-and-whether-it-improved-5"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-5 --> *(The replication's own abstract states the baseline as 36.54%, which does not reconcile with the original's published 219 of 571. The discrepancy traces to a single mis-transcribed cell in its comparison table. This survey uses the original's published figure.)*

<a id="p-161-insecure-code-generation-and-whether-it-improved-6"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-6 --> **And on a realistic task, the improvement does not show up at all.** A 2026 study of developers implementing security-sensitive API usage found **no statistically significant security benefit** from assistant use — every implementation in both the assisted and unaided conditions remained insecure <!-- cite:129 --> [[129]](references.md#ref-129). Scenario benchmarks and developer studies are measuring different things, and the second is closer to what deployment looks like.

<a id="p-161-insecure-code-generation-and-whether-it-improved-7"></a><!-- para:161-insecure-code-generation-and-whether-it-improved-7 --> The hopeful counterpoint is that security is *steerable*: property-specific prefixes with frozen weights raise a 2.7B model's secure-generation rate from 59.1% to 92.3% while preserving functional correctness — and the same lever run adversarially drives it down to 36.8% <!-- cite:42 --> [[42]](references.md#ref-42). Explicitly dual-use.

### <a id="sec-16.2"></a>16.2 The Agentic Attack Surface: What Is Measured

<a id="p-162-the-agentic-attack-surface-what-is-measured-1"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-1 --> Autonomous agents (<!-- secxref:12 -->[§12](agentic-coding-systems.md#sec-12)) introduce **indirect prompt injection**: the agent ingests untrusted content and may treat it as instruction rather than data.

<a id="p-162-the-agentic-attack-surface-what-is-measured-2"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-2 --> **Scope this honestly, because the measured literature and the motivating worry are not the same thing.** The intuitive threat — an agent reads a repository, so an attacker who can write an issue body, a README, a code comment, or a dependency can talk to it — is widely asserted and, in the sources acquired for this survey, **unmeasured**. What *is* measured is a different channel: the external-tool interface, where an attacker controls a tool's **description** or its **return value**, plus one qualitative case study of a poisoned agent-skill file. The survey states the distinction rather than pooling the two.

<a id="p-162-the-agentic-attack-surface-what-is-measured-3"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-3 --> **The measured attack is two-stage, and the second stage is the hard one.** The attacker must first get a malicious tool into the victim's toolset — a supply-chain or name-spoofing problem, and a survey of 67,057 public tool servers found 212 vulnerable to maintainer hijacking and 304 to redirection hijacking, i.e. under 1% <!-- cite:126 --> [[126]](references.md#ref-126) — and must then know enough of the agent's internal prompt to craft the lure. That second precondition carries the whole result: attack success runs **0.20 without the prompt against 0.71 with a partially leaked one** <!-- cite:125 --> [[125]](references.md#ref-125).

<a id="p-162-the-agentic-attack-surface-what-is-measured-4"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-4 --> **Three success-rate families, on their own bases, deliberately not averaged:**

- <a id="p-162-the-agentic-attack-surface-what-is-measured-5"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-5 --> **Simulated agents** (prompt reconstructions, 100 cases per cell): mean success 0.70, 0.82, 0.87 as the attack is fitted on 2, 4 and 8 samples, against a best prior baseline of 0.50 and three other published attacks at 0.02, 0.00 and 0.00 <!-- cite:125 --> [[125]](references.md#ref-125).
- **Real production agents**, same payloads transferred unmodified: mean **0.50**, ranging 0.34 to 0.72 across five named products, against 0.02 for the prior baseline — with the drop from simulation attributed by the authors to proprietary defences and the simulation-to-reality gap <!-- cite:125 --> [[125]](references.md#ref-125).
- **Version-pinned red-teaming**: two-channel attacks reach 0.8–1.0 on most older agent versions, description-only attacks mostly 0.0–0.6 <!-- cite:126 --> [[126]](references.md#ref-126).

> <a id="p-162-the-agentic-attack-surface-what-is-measured-6"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-6 --> **Note — ten trials is not a rate.** The version-pinned results use **10 attempts per cell**. A reported 0.0 has a Wilson 95% interval of [0.00, 0.28]; a reported 0.3 spans [0.11, 0.60]; a reported 1.0 spans [0.72, 1.00]. So "hardened to zero" is consistent with a true success rate near one in four. This survey supplies the intervals the papers omit, and treats the hardening result as *directional and large* rather than as elimination.

<a id="p-162-the-agentic-attack-surface-what-is-measured-7"></a><!-- para:162-the-agentic-attack-surface-what-is-measured-7 --> **One defence has a proper control, and it is architectural rather than prompt-level.** Because that study pins agent versions, the old-versus-new comparison holds the backend model fixed: one product goes from 1.0 to 0.1–0.2 across a major version change, another from 0.6–0.7 to 0.0, on identical backends <!-- cite:126 --> [[126]](references.md#ref-126). The mechanism is progressive disclosure — surfacing tool *names* without their descriptions, so the description-channel lure never reaches the model at all. Prompt-level defences (sandwiching, spotlighting, perplexity filters) are reported as a clear negative result: they move the numbers marginally. The lesson generalizes past this channel — **the effective mitigation removed the attacker-controlled text from the context, rather than instructing the model to resist it.**

### <a id="sec-16.3"></a>16.3 Gaming the Verifier

<a id="p-163-gaming-the-verifier-1"></a><!-- para:163-gaming-the-verifier-1 --> The argument of <!-- secxref:8 -->[§8](instruction-tuning-and-alignment.md#sec-8) is that code's advantage is a reward an oracle can compute. The corresponding risk is that an oracle can be attacked. The strongest published evidence is a curriculum study in which models trained on early, mild specification-gaming environments **generalize to later, unseen tampering** — including, in a small fraction of cases, editing the reward mechanism itself and then writing output that conceals the edit <!-- cite:118 --> [[118]](references.md#ref-118). The rates are low and the setting is deliberately constructed, so this is an existence proof rather than a base rate. It is nonetheless the concrete form of the concern that <!-- secxref:J.3 -->[§J.3](appendix-j-code-derivations.md#sec-J.3) raises about replacing a learned reward model with a rule: a compiler cannot be flattered, but a test suite can be rewritten, and an agent with repository write access can reach its own tests.

### <a id="sec-16.4"></a>16.4 Licensing, Copyright, and Memorization

<a id="p-164-licensing-copyright-and-memorization-1"></a><!-- para:164-licensing-copyright-and-memorization-1 --> Because code carries licenses, training on it raises questions prose does not. The bellwether is the Doe v. GitHub class action: filed in 2022 with 22 claims, largely narrowed by a 2024 ruling that dismissed most of them, leaving primarily an open-source-license-violation claim and a breach-of-contract claim, and proceeding on appeal — **still unresolved at the time of writing** <!-- cite:53 --> [[53]](references.md#ref-53). Notably, the copyright-management-information claim was dismissed on a finding that the tool "rarely memorized code" and did not reproduce the plaintiffs' work identically, which ties the legal question directly to the technical one: the strength of a copyright claim depends on demonstrable regurgitation <!-- cite:53 --> [[53]](references.md#ref-53).

<a id="p-164-licensing-copyright-and-memorization-2"></a><!-- para:164-licensing-copyright-and-memorization-2 --> The open ecosystem's answer is licensing-by-construction (<!-- secxref:6 -->[§6](pretraining-data.md#sec-6)): permissive-only selection with a developer opt-out, an attempt to make training data defensible rather than litigating afterwards <!-- cite:7 --> [[7]](references.md#ref-7), <!-- cite:9 --> [[9]](references.md#ref-9). Its successor corpus loosened this, including unlicensed files alongside permissive ones while continuing to exclude copyleft <!-- cite:9 --> [[9]](references.md#ref-9) — a policy choice worth noticing, since "no license detected" is legally closer to all-rights-reserved than to permissive.

<a id="p-164-licensing-copyright-and-memorization-3"></a><!-- para:164-licensing-copyright-and-memorization-3 --> Two gaps this survey flags rather than papers over: the status of models trained indiscriminately on copyleft code is genuinely unsettled law, and **memorization measurement for code is underdeveloped** — which matters more than it looks, because the one dismissed claim above turned on exactly that empirical question.
