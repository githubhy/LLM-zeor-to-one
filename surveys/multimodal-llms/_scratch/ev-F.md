## Q1 — Whisper front-end + encoder, exact numbers

- **Mel spectrogram spec** — "an 80-channel log-magnitude Mel spectrogram representation is computed on 25-millisecond windows with a stride of 10 milliseconds" — *source:* `radford-whisper-2022.pdf` §2.2, p.3 — *quality:* verbatim

- **Encoder/decoder symmetry** — "The encoder and decoder have the same width and number of transformer blocks." — *source:* `radford-whisper-2022.pdf` §2.2, p.3 — *quality:* verbatim

## Q2 — AudioPaLM discrete audio tokens

- **Tokenization pipeline (general)** — "We follow the process of Lakhotia et al. [2021], Borsos et al. [2022] to convert raw waveforms into tokens. This involves extracting embeddings from an existing speech representation model and subsequently discretizing those embeddings into a limited set of audio tokens. Borsos et al. [2022] extract embeddings from the w2v-BERT model [Chung et al., 2021] and quantize them via k-means." — *source:* `rubenstein-audiopalm-2023.pdf` §3.1 "Audio Embeddings and Tokenization", p.4 — *quality:* verbatim
- **w2v-BERT tokenizer variant** — "We follow the procedure described in Borsos et al. [2022] with two modifications. First, we use a w2v-BERT model that has been trained on multilingual data... Second, we do not normalize the embeddings before performing the k-means clustering... This method produces tokens at a rate of 25Hz and the token vocabulary is of size 1024." — *source:* `rubenstein-audiopalm-2023.pdf` §3.1, p.5 (first bullet) — *quality:* verbatim
- **USM-v1 tokenizer variant** — "We perform the same procedure with the more performant Universal Speech Model (USM) encoder [Zhang et al., 2023a] instead of the w2v-BERT encoder. We use the largest 2B parameter variant of this multilingual speech encoder and extract embeddings from the middle layer. Similar to w2v-BERT, this method produces tokens at a rate of 25Hz and the token vocabulary is of size 1024." — *source:* `rubenstein-audiopalm-2023.pdf` §3.1, p.5 (second bullet) — *quality:* verbatim
- **USM-v2 tokenizer variant** — "We additionally experiment with a quantizer that is trained with an auxiliary ASR loss. This version has been finetuned further to provide better multilingual performance. As with USM-v1, this method accepts raw audio as input and returns a sequence of integers with length proportional to the length of audio as output." Token rate / codebook size NOT restated numerically for USM-v2 in this passage (no explicit "25Hz"/"1024" attached to this bullet) — *source:* `rubenstein-audiopalm-2023.pdf` §3.1, p.5 (third bullet) — *quality:* verbatim (gap noted)
- **Codebook size = clustering method** — k-means clustering over embeddings, producing token vocabulary size 1024 (both w2v-BERT and USM-v1 variants) — *source:* `rubenstein-audiopalm-2023.pdf` §3.1, p.4-5 — *quality:* verbatim
- **Vocabulary-extension mechanism (embeddings matrix)** — "In a Transformer decoder, the first layer of the model after input preprocessing is the token embeddings matrix $\mathbf{E}$ which maps integer-valued tokens to dense embeddings; given a vocabulary of $t$ tokens and embeddings of size $m$, $\mathbf{E}$ is a $t \times m$ matrix... The rest of the decoder architecture is completely agnostic to the number of tokens modelled. Therefore we only need to make one small modification to turn a text-only model into one that models both text and audio: we expand the size of the embeddings matrix $\mathbf{E}$ to be of size $(t+a) \times m$ where $a$ is the number of audio tokens (the size of $\mathbf{E}' = \mathbf{E}^\top$ changes accordingly)." — *source:* `rubenstein-audiopalm-2023.pdf` §3.2 "Modifying text-only decoders to model both text and audio", p.5 — *quality:* verbatim
- **New-row indexing + initialization (architecture description)** — "In order to make use of pretrained text models, we change the existing model checkpoints by adding $a$ new rows to the embeddings matrix $\mathbf{E}$. An implementation detail is that the first $t$ tokens (from zero to $t$) correspond to the SentencePiece text tokens while the next $a$ tokens (from $t$ to $t+a$) represent audio tokens. While we can re-use the text embeddings of the pre-trained model, the new audio embeddings are freshly initialized and must be trained. We found it necessary to train all model weights rather than keeping the previous weights fixed." — *source:* `rubenstein-audiopalm-2023.pdf` §3.2, p.5 — *quality:* verbatim
- **New-row initialization (specific experimental value used for main results)** — "As an initial checkpoint, we use a PaLM-2 8B checkpoint [Anil et al., 2023] to which we add the capability to process audio tokens as input and output as described in Section 3.2. The additional audio token embeddings are initialized to 0." — *source:* `rubenstein-audiopalm-2023.pdf` §5.1, p.9 — *quality:* verbatim

## Q4 — Video token budget + M-RoPE

### Qwen2-VL — M-RoPE

- **M-RoPE decomposition, definition** — "Another key architectural enhancement is the innovation of Multimodal Rotary Position Embedding (M-RoPE). Unlike the traditional 1D-RoPE in LLMs, which is limited to encoding one-dimensional positional information, M-RoPE effectively models the positional information of multimodal inputs. This is achieved by deconstructing the original rotary embedding into three components: temporal, height, and width." — *source:* `wang-qwen2-vl-2024.pdf` §2.1 "Multimodal Rotary Position Embedding (M-RoPE)", pp.4-5 — *quality:* verbatim
- **Per-modality ID assignment rule** — "For text inputs, these components utilize identical position IDs, making M-RoPE functionally equivalent to 1D-RoPE (Su, 2024). When processing images, the temporal IDs of each visual token remain constant, while distinct IDs are assigned to the height and width components based on the token's position in the image. For videos, which are treated as sequences of frames, the temporal ID increments for each frame, while the height and width components follow the same ID assignment pattern as images. In scenarios where the model's input encompasses multiple modalities, position numbering for each modality is initialized by incrementing the maximum position ID of the preceding modality by one." — *source:* `wang-qwen2-vl-2024.pdf` §2.1, p.5 — *quality:* verbatim
- **Claimed benefit** — "M-RoPE not only enhances the modeling of positional information but also reduces the value of position IDs for images and videos, enabling the model to extrapolate to longer sequences during inference." — *source:* `wang-qwen2-vl-2024.pdf` §2.1, p.5 — *quality:* verbatim

### Qwen2-VL — Naive Dynamic Resolution

- **Mechanism** — "A key architectural improvement in Qwen2-VL is the introduction of naive dynamic resolution support (Dehghani et al., 2024). Unlike Qwen-VL, Qwen2-VL can now process images of any resolution, dynamically converting them into a variable number of visual tokens. To support this feature, we modified ViT by removing the original absolute position embeddings and introducing 2D-RoPE (Su et al., 2024; Su, 2021) to capture the two-dimensional positional information of images. At the inference stage, images of varying resolutions are packed into a single sequence, with the packed length controlled to limit GPU memory usage." — *source:* `wang-qwen2-vl-2024.pdf` §2.1 "Naive Dynamic Resolution", p.4 — *quality:* verbatim
- **Token-compression step (2×2 merge + special tokens)** — "Furthermore, to reduce the visual tokens of each image, a simple MLP layer is employed after the ViT to compress adjacent 2 × 2 tokens into a single token, with the special <|vision_start|> and <|vision_end|> tokens placed at the beginning and end of the compressed visual tokens. As a result, an image with a resolution of 224 × 224, encoded with a ViT using patch_size=14, will be compressed to 66 tokens before entering LLM." — *source:* `wang-qwen2-vl-2024.pdf` §2.1, p.4 — *quality:* verbatim
- **Worked-example arithmetic check (paper's own numbers)** — 224/14 = 16 patches per side → 16×16 = 256 ViT patch tokens → 2×2 MLP merge → 256/4 = 64 compressed tokens → +2 special tokens (<|vision_start|>, <|vision_end|>) = **66 tokens**, matching the paper's stated figure exactly — *source:* derived from `wang-qwen2-vl-2024.pdf` §2.1 p.4 numbers (224, patch_size=14, 2×2 merge, "66 tokens" all paper-stated) — *quality:* paraphrase/derived, self-consistent with the paper's own quoted result
- **Figure 2 worked multi-image/video token-count example** — Figure 2 caption/diagram gives four concrete inputs and their resulting token counts: "Picture 1" (Height 8204, Width 1092) → 11427 tokens; "Picture 2" (Height 28, Width 224) → 8 tokens; "Picture 3" (Height 700, Width 1260) → 1125 tokens; "Video 1" (Height 336, Width 644, Time 16s) → 2208 tokens — *source:* `wang-qwen2-vl-2024.pdf` Figure 2, p.4 — *quality:* verbatim (figure transcribed; the paper gives no intermediate arithmetic for these four numbers, so they are recorded as given, not independently re-derived)
